# 单入口工作流与状态机

本文件定义 CUMCM 项目如何前进、暂停和回退。具体文件路径、字段和 Schema 由 [产物契约](contracts.md) 定义；本文件只定义状态语义。

## 运行模式

本轮工作方式从 `focused`、`competition-fast`、`release-strict` 和 `audit` 中选择，定义与 manifest 映射见 [工作方式](profiles.md)。这些模式不改变本文件的状态含义，也不是新的 manifest 枚举。

- `focused` 不要求建立完整状态或未经历的门禁。
- `competition-fast` 复用 `project`/`run`，可以集中提示四组人工复核，但各门禁仍分别落盘。
- `release-strict` 复用 `release`，保留完整 G0–G7 和发布闭包。
- `audit` 默认只读，只有用户明确要求后才修复。

续做项目先读取当前工作树和审计报告，核对上游散列、当前 approval set 与失效传播，再从 `next_legal_action` 原地继续。“文件存在”不等于“状态完成”，不得重新初始化或凭 Markdown 描述跳过证据。

## 主状态

| 状态 | 主要工作 | 进入下一状态的必要证据 |
|---|---|---|
| INTAKE | 识别赛题、附件、已有产物、团队、模式和截止时间 | 输入清单、项目范围、project manifest |
| WAIT_G0 | 等待输入确认 | G0 人工批准绑定当前题面和附件指纹 |
| FRAMING | 拆分顶层问题，分析字段、单位、歧义、依赖和成功判据 | problem_spec |
| WAIT_G1 | 等待问题确认 | G1 人工批准绑定当前 problem_spec |
| MODELING | 构造基线和必要候选，建立数学模型 | model_spec 及预定验证计划 |
| WAIT_G2 | 等待模型确认 | G2 人工批准绑定当前 model_spec |
| EXPERIMENT_DESIGN | 固定数据切分、指标、基线、预算、种子和接受规则 | experiment |
| WAIT_G3 | 等待实验方案确认 | G3 人工批准绑定当前 experiment |
| COMPUTING | 实现数据流程、模型和实验，保留每次运行 | 可运行入口和不可变原始输出 |
| VALIDATING | 做条件性验证、复现、约束和不确定性检查 | results 及验证证据 |
| WAIT_G4 | 等待结果确认 | G4 人工批准绑定当前 results |
| CLAIMING | 把可成立的结论和图表绑定到结果 | claims、figures |
| WAIT_G5 | 等待结论与图表确认 | G5 人工批准绑定当前 claims 和 figures |
| WRITING | 只由已确认的证据形成中文论文 | 正文、引用和结论映射 |
| FINAL_QA | 编译、视觉检查、数值核对和独立复核 | 最终 PDF 和论文审计 |
| WAIT_G6 | 等待论文确认 | G6 人工批准绑定当前论文 |
| RELEASE_QA | 汇总 manifest、运行入口、环境、证据和交付物 | release manifest 和最终审计 |
| WAIT_G7 | 等待最终科学签核 | G7 人工批准绑定完整发布包 |
| SUBMISSION_READY | 质量工作流完成 | 不再自动增加模型或改动结论 |

WAIT_INPUT 是暂停原因，不是跳过阶段的通道。缺输入时记录所缺内容、影响范围和可继续的部分。

## 八个人工门禁

WAIT_G0 至 WAIT_G7 只有在对应人工 review 为 PASS，且自动审计不存在 BLOCK、ENV_BLOCK 或 STALE 时才能退出。人工 PASS 不能抵消机器发现的硬错误；机器检查通过也不能代替人工判断。

release 中的门禁批准按 `approval_set_id` 聚合。需要交叉复核的门禁必须由不同 `member_id` 对完全相同的证据指纹分别签核；G7 由三名成员共同签核并绑定当前 `snapshot:release`。审计器只接受当前且完整的 approval set，不以数组中最后一条单人 PASS 代替团队决定。

### manifest 门禁分层

| manifest_type | 缺少当前人工 approval set | 含义 |
|---|---|---|
| `project` / `run` | `WARN` | 人工复核仍待完成；门禁未通过，不得称为可提交 |
| `release` | `BLOCK` | 发布闭包不完整，不能达到 `SUBMISSION_READY` |

release 的当前角色要求保持为：

- G0：至少一名已声明成员签核；
- G1、G2、G5、G6、G7：三名已声明成员全部签核；
- G3、G4：至少覆盖 `modeling` 与 `computation` 两类独立角色。

以上是现有审计语义，不是身份认证机制。角色和人数通过 review 契约核对；签核真实性仍由人类读取 review 与证据确认。project/run 的 `WARN` 不能解释为阶段通过，也不能因为比赛时间紧而升级为 `PASS`。

### G0：输入确认

确认当前题面、题号、附件、数据版本和已有项目材料互相对应，输入清单及散列完整。G0 只确认“用的是哪一组材料”，不证明文件内容正确。

### G1：题意冻结

确认：

- 顶层问题数量和依赖关系；
- 输入、输出、评价口径和单位；
- 对关键歧义采用的解释及理由；
- 数据字段、缺失和异常的处置边界；
- 每问的成功判据。

正式三人团队应由三人共同确认。训练时若缺少独立复核者，可以由当前用户确认，但必须记录“未独立复核”。

### G2：模型冻结

确认：

- 简单基线可执行；
- 每个子模型对应明确任务；
- 假设、变量、目标、约束、边初值条件和单位完整；
- 参数有识别来源；
- 验证方案能够发现模型失效；
- 模型接口和误差传播清楚；
- 复杂度与数据和剩余时间匹配。

建模负责人批准，计算负责人复核可实现性，综合负责人确认结果将可表达。

### G3：实验方案冻结

确认：

- 数据版本、切分和预处理顺序明确；
- 候选比较使用共同数据、指标和预算；
- 基线、种子、重复次数和参数搜索预算明确；
- 主要结果产生前已登记接受规则和失败规则；
- 每条接受规则标明 `pre_result` 或 `post_result`；后者不被包装成预注册确认性证据；
- 输出、日志和环境信息足以复现；
- 探索性实验与确认性实验有明确区分。

计算负责人批准，建模负责人复核比较是否回答模型问题。

### G4：结果冻结

确认：

- 关键代码可从登记入口重跑；
- 输入、环境、参数、种子和运行 ID 齐全；
- 预测、优化、排序、仿真等适用验证已经完成；
- 关键数值、图表和定性结论均有结果 ID；
- 已知失败、不确定性和适用范围未被隐藏。

计算负责人批准，建模负责人复核数学一致性。

### G5：结论与图表冻结

确认：

- 每个准备写入论文的核心结论都有 result 或证明证据；
- 因果、全局最优和显著性等高强度措辞没有越过证据；
- 图表记录数据、运行和生成程序；
- 不确定性、反证和适用范围没有被隐藏；
- 定性解释和定量结果没有错配。

综合负责人批准，计算负责人核对数值，建模负责人核对推断力度。

### G6：论文冻结

确认摘要、公式、数值、图表、引用和结论映射一致，PDF 编译与逐页视觉检查通过，不存在占位符、内部工作流文字或无法追溯的关键数字。

综合负责人首责，另两人分别完成语义和数值复核。

### G7：最终发布冻结

确认 release manifest、最终 PDF、论文源码、运行入口、环境、结果、图表、验证报告和已知限制构成同一版本的完整交付包。

三名成员共同批准。Agent 不得代签任何门禁。

## 回退与失效

| 发生变化或失败 | 最早回退状态 | 自动失效内容 |
|---|---|---|
| 题面、附件或输入版本变化 | INTAKE | G0 至 G7 及全部下游 |
| 题意解释、顶层问题、单位或字段定义变化 | FRAMING | G1 至 G7、模型、实验、结果、论文 |
| 重要假设、变量、目标、约束或模型结构变化 | MODELING | G2 至 G7、实验、结果、相关论文 |
| 数据切分、指标、基线、种子、预算或接受规则变化 | EXPERIMENT_DESIGN | G3 至 G7、结果和论文 |
| 清洗实现、代码、求解器或运行参数变化 | COMPUTING | G4 至 G7、受影响结果和论文结论 |
| 结果选择、指标计算或不确定性结论变化 | VALIDATING | G4 至 G7、结论、图表和摘要 |
| 结论措辞或图表数据映射变化 | CLAIMING | G5 至 G7、论文 |
| 只修改不改变含义的排版和文字 | WRITING | G6、G7；G0 至 G5 可保留 |
| 论文出现无法追溯的新结论 | CLAIMING | G5 至 G7，直至补齐证据或删除结论 |

任何上游修改都应保留旧版本和旧运行记录，只标记为过期。禁止静默覆盖，也不要通过删除失败实验制造“全都成功”的印象。

## 自动迭代边界

- 拼写、路径、格式、确定性代码错误可自动修复并复查。
- 同一根因连续失败两次，应停止重复尝试并报告诊断。
- G0 至 G3 后出现会改变输入、现实含义、模型结构或实验设计的修改，必须重新获得对应人工批准。
- 随机实验只执行预先登记的重复次数；新增重复或改指标需要说明原因。
- 到达 G4 后，除非发现实质错误，不再引入新算法；正式赛模式尤其应保护写作和最终检查时间。

## 状态汇报格式

审计器从当前门禁、硬失败和失效根确定性派生四个恢复字段：`workflow_state`、`last_valid_gate`、`rollback_target` 和 `next_legal_action`。`last_valid_gate` 是从 G0 起连续有效的最后门禁；存在 `BLOCK`、`ENV_BLOCK` 或 `STALE` 时，`rollback_target` 指向最早失败门禁对应的工作状态，`workflow_state` 与之对齐。没有硬失败但仍有未批准门禁时停在对应 `WAIT_Gn`；release 的 G0–G7 全部有效后才是 `SUBMISSION_READY`，非 release 项目即使阶段证据齐全也停在 `RELEASE_QA`。续做项目必须使用这些派生字段，不重新初始化或凭文件存在猜测进度。

每次推进后至少报告：

~~~text
当前状态：
本轮输入：
新建或更新产物：
检查结果：
失效或待补证据：
待人工门禁：
下一合法动作：
结论置信度：
~~~
