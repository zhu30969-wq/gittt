# 论文与交付

仅在组织论文、生成图表说明、选择排版引擎或做最终质量检查时读取本文件。论文是证据链的消费者，不是重新计算结果的地方。

## 1. 写作前置条件

开始正文前先确认：

1. `problem_spec` 中每个子问题都有明确交付目标；
2. 采用的模型和基线已经冻结；
3. 论文要使用的结果均来自成功且未过期的实验；
4. 每个关键结论已登记到 `claims/claims.yaml`，并关联结果、指标、图或推导；
5. 图表均能追溯到生成代码、数据和运行记录。

缺少上述任一条件时，先回到最早失效阶段。不要在正文中临时补算、猜测或平滑一个数值。

## 2. 从证据图生成论文

先构造以下映射，再扩写段落：

```text
子问题
  -> 现实目标和判断标准
  -> 假设与变量
  -> 基线和最终模型
  -> 求解或估计方法
  -> 关键结果 ID
  -> 验证与反证
  -> 可成立的结论
  -> 局限与适用域
```

每个核心结论在源码附近保留稳定标记，例如 LaTeX 注释 `% claim:C-Q1-03` 或 Typst 注释 `// claim:C-Q1-03`。标记用于审计，不应出现在最终排版文本中。

## 3. 推荐叙事结构

以当次选用的模板为准；通常应覆盖：

- 摘要与关键词；
- 问题重述与任务分解；
- 问题分析；
- 假设、理由和影响；
- 符号、单位和定义；
- 各子问题的模型、求解、结果与验证；
- 敏感性、稳健性或不确定性分析；
- 模型优缺点、适用范围与可推广内容；
- 参考文献；
- 支撑复现所需的附录。

结构服务论证，不要为凑章节机械增加模型。一个可靠基线、一个有依据的改进和充分验证，通常优于多个互不关联的算法名称。

## 4. 摘要最后写

摘要必须回答“做了什么、得到什么、为何可信”。对每个子问题尽量给出：

- 任务和采用的方法；
- 至少一个有区分度的精确结果或决策；
- 最关键的验证、误差或稳健性证据；
- 结论的适用范围。

不要把摘要写成章节目录，也不要使用“效果良好”“具有一定价值”等无证据句子。若结果不能用一个数字概括，可给出区间、排序稳定性、约束可行率或主要机制判断。

## 5. 数值与措辞约束

- 论文中的数值只从已登记结果读取，并按 `claims/claims.yaml` 中的数值断言、单位和容差呈现；
- 派生的百分比、差值、比值和敏感性增量同样先登记为 result metric；不能在正文或表格中临时手算后绕过 numeric assertion；
- 看到结果后才形成的判断规则必须写明是探索性或事后登记，不得使用“预先”“预注册”等措辞；确认性结论需要新的、结果前冻结的实验；
- 同一指标统一名称、单位、样本范围和小数位；
- “显著”“最优”“提升”“稳健”“预测准确”等词必须有对应检验或比较；
- 启发式算法没有有效证书时，只能写“本次搜索得到的最好解”或等价表述；
- 相关性不自动支持因果结论；
- 训练集拟合不支持泛化结论；
- 敏感性图不等于完整验证，必须解释扰动范围和判断标准；
- 失败实验和不利证据不能被静默删除，应说明它们如何影响模型选择或结论边界。

## 6. 图表质量

每张图只承担清晰的论证任务。最低要求：

- 坐标轴、图例、单位、样本范围和数据来源明确；
- caption 能独立说明图中对象、条件和主要发现；
- 颜色、线型或标记在灰度和色觉差异下仍可区分；
- 不截断坐标轴来夸大差异，不用双轴制造虚假相关；
- 误差条、区间或重复实验分布与正文口径一致；
- 概念图不得作为定量结论的唯一证据；
- 手工调整过的图必须保留原始生成物和修改说明。

## 7. 可选 Word 派生交付

需要可编辑 Word 时，保留冻结的 `.tex` 或 `.typ` 作为 canonical paper entrypoint，再从同一证据版本生成 `.docx`。Word 是派生交付物，不能替代可审计源稿，也不能成为新的数值来源。

- 只有实际生成成功后才把 `.docx` 登记到 release manifest；路径、稳定 typed ID 和 SHA-256 必须对应当前文件；
- 当 Word 是明确交付要求时将其标为 `required: true`，否则不必在 manifest 中声明空的可选项；
- 转换后逐项核对公式、上下标、图片、三线表、交叉引用、页眉页脚、中文字体、分页和目录；
- 将 DOCX 渲染为 PDF 或逐页图片做视觉比较，不能用“文件能打开”代替排版验收；
- 若 `.docx` 与 canonical source 的数值或结论不一致，以冻结证据和 canonical source 为准，修复转换链后重新生成并更新散列。

当前通用审计器只验证 DOCX 的存在性、路径和散列；它不自动证明 Word 内部公式、分页或视觉布局正确。只有在另有 DOCX 内容/渲染 QA 证据时，才可声明 Word 排版也已通过质量审计。

## 8. 排版引擎隔离

项目开始时选定 LaTeX 或 Typst，并在本次项目内保持一致。只有原引擎不可用或模板明确要求时才切换；切换后重新做整篇编译和视觉检查。

LaTeX 重点检查：

- 缺失的 `\label`、`\ref`、`\cite` 和图片路径；
- 未授权的 shell escape 或 `\write18`；
- 交叉引用是否需要再次编译；
- 过宽公式、浮动体顺序和字体嵌入。

Typst 重点检查：

- 残留的 LaTeX 命令或数学语法；
- 标签、引用、图片和公式编号；
- 模板导入路径和字体可用性；
- 页面溢出与标题孤行。

不要同时加载两套模板知识，也不要通过字符串替换把一种引擎的源码“翻译”为另一种后直接交付。

## 9. 最终视觉检查

编译成功只是必要条件。将 PDF 逐页渲染为图片并检查：

- 摘要、标题、页码和章节层级；
- 公式、表格、图片、caption 是否截断或重叠；
- 字号、留白、分页、孤行和连续大块空白；
- 图中文字是否可读，表格是否需要横置或拆分；
- 引用、编号、目录项和附录跳转；
- PDF 元数据、正文和图表中是否残留内部工作流名称或临时标记。

视觉检查由人完成最终判断。自动 lint 未报错不能替代逐页阅读。

## 10. 交付包

交付前创建 release manifest，至少列出：

- 最终论文 PDF 及其 SHA-256；若生成派生 Word，也登记 DOCX 的稳定 ID、角色和 SHA-256；
- 论文源码和构建入口；
- 完整可运行代码及环境锁；
- 输入数据或合法获取说明；
- 运行命令、随机种子和预期输出；
- 结果、图表和 claims 清单；
- 验证与复现报告；
- 已知限制和未解决警告。

最终报告必须区分 `PASS`、`WARN`、`BLOCK`、`ENV_BLOCK` 和 `STALE`。不要把“文件存在”写成“模型正确”，也不要把内部就绪度评分解释为获奖概率。
