# 三人团队协作与交接

CUMCM 团队通常由三人共同完成。角色用于明确首责和复核，不意味着其他成员可以不了解整体模型。

## 三类责任

| 责任 | 首要职责 | 必须交叉理解 |
|---|---|---|
| 建模负责人 | 题意、假设、变量、方程、目标、约束、候选选择 | 能阅读关键代码和解释主要结果 |
| 计算负责人 | 数据、代码、实验、求解、图表、复现 | 能解释模型假设和论文中的关键公式 |
| 综合负责人 | 决策记录、结果追溯、论文、摘要、排版、最终审计 | 能说明结果来源和验证局限 |

角色可按题目和成员能力调整，也可在不同子问题轮换。每个关键产物必须有一名负责人和至少一名不同成员复核。

## 单一事实源

团队通过结构化产物交接，不以口头消息作为最终依据：

- 题意和数据定义以问题规格为准；
- 数学关系以模型规格和稳定方程 ID 为准；
- 运行结果以不可变运行 ID 为准；
- 论文数值以结论与结果映射为准；
- 阶段完成以人工批准记录及其产物散列为准。

聊天记录、临时截图和个人笔记只能作为讨论材料，不能覆盖事实源。

## 三次主要交接

### 建模负责人 → 计算负责人

必须提供：

- 已批准的问题规格；
- 变量、参数、单位和索引；
- 方程、目标、约束、边初值条件；
- 假设与适用范围；
- 每个子问题的输入输出接口；
- 可手算小例、极端情况或预期性质；
- 基线和候选比较方案；
- 未解决问题。

计算负责人必须确认模型可实现，不能在代码中静默修改约束或变量含义。需要改动时回到模型记录。

### 计算负责人 → 综合负责人

必须提供：

- 数据版本和转换规则；
- 运行入口、环境、参数和随机种子；
- 关键运行 ID；
- 结果、指标、图表及其来源；
- 约束残差、误差、收敛或稳定性证据；
- 失败实验和已知局限；
- 允许写入论文的结论清单。

仅提供图片或口头报数不构成交接。

### 综合负责人 → 建模与计算负责人

必须提供：

- 论文结论到结果 ID 的映射；
- 公式和符号的一致性检查；
- 摘要中的关键数值；
- 被压缩或省略的假设和限制；
- 待核实的解释、引用和图表；
- 最终 PDF 中发现的问题。

建模负责人核对语义，计算负责人核对数字和图表。两者均不得只检查自己撰写的段落。

## 人工门禁责任

| 门禁 | 首责 | 复核与确认 |
|---|---|---|
| G0 输入确认 | 综合负责人 | 建模、计算负责人核对题面与附件 |
| G1 问题确认 | 建模负责人 | 三人共同确认 |
| G2 模型确认 | 建模负责人 | 计算负责人复核，综合负责人确认可表达 |
| G3 实验确认 | 计算负责人 | 建模负责人复核比较与验证设计 |
| G4 结果确认 | 计算负责人 | 建模负责人复核数学一致性 |
| G5 结论与图表确认 | 综合负责人 | 计算负责人核数，建模负责人核推断 |
| G6 论文确认 | 综合负责人 | 建模、计算负责人交叉复核 |
| G7 最终发布确认 | 综合负责人 | 三人共同确认 |

批准记录必须包含：

- 门禁 ID；
- 产物及散列；
- 批准人；
- 时间；
- 保留意见；
- 下一阶段负责人。

Agent 只能把门禁写成待批准或记录用户明确给出的批准，不能代替成员签字。

## 并行工作的边界

适合并行：

- 数据概况与题意歧义整理；
- 不同候选的可行性调查；
- 代码实现与论文结构占位；
- 图表风格准备与参考文献核实；
- 独立检查同一结果。

不适合并行写入同一事实：

- 同一变量定义；
- 同一约束或目标；
- 同一结果数字；
- 同一摘要终稿；
- 同一门禁状态。

对共享文件指定唯一合并负责人。其他成员通过建议、补丁或独立分支提交，避免同时覆盖。

## 交接记录模板

~~~yaml
handoff_id: H2
from_role: computation
to_role: synthesis
state: VALIDATING
artifacts:
  - id: result-main
    hash: pending
run_ids: []
checks_passed: []
known_failures: []
open_questions: []
requested_acknowledgement: true
~~~

散列、运行 ID 和检查项必须填写实际值，不能保留示例占位符后进入下一门禁。

## 分歧解决

发生分歧时按以下顺序处理：

1. 确认双方是否使用同一题意、单位、数据版本和指标；
2. 把意见写成可检验的两个候选；
3. 优先设计最小成本、最大区分度的实验或手算检查；
4. 比较任务适配、验证证据、可解释性和剩余时间；
5. 记录最终决定以及被拒绝路线；
6. 若证据仍不足，采用更保守的表述并标记需验证。

资历、算法复杂度和论文篇数不能替代证据。

## 时间与冻结

项目开始时记录题意冻结、模型冻结、结果冻结和最终检查的内部时间点。正式赛模式下：

- 未到 G1 不进行大规模编码；
- 未到 G3 不投入高成本参数搜索；
- G3 后不随意增加候选；到 G4 后除发现实质错误外停止增加新算法；
- 为论文、复现和 PDF 检查保留独立时间；
- 发现实质错误时允许回退，不能为了维持进度隐藏问题。

训练模式可安排更多回退和角色轮换，但仍使用同一交接格式。

## 交叉理解检查

进入 G7 前，三名成员应分别能回答：

- 每问要解决什么，为什么采用当前模型；
- 最重要的假设和失效条件是什么；
- 关键数字来自哪个运行和哪项验证；
- 模型相对基线改善了什么；
- 论文最薄弱的结论是什么。

任何关键问题只有一人能够回答时，团队协作尚未完成。
